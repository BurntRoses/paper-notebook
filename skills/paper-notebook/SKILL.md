# Paper Notebook

Before generation or updates, read [mandatory quality workflow](references/quality-workflow.md) and the complete [Chinese writing rules](references/chinese-writing.md). Check the published runtime manifest before reusing cached files; when release differs, verify and replace managed runtime files with the current package while preserving authored files and user records. Re-read updated instructions. A build is a draft; final delivery requires the source-bound `finalize` gate, completed chapter review and recorded browser coverage or a specific unavailable capability.

Generate a tutorial with the shared reader. Deliver one clearly named offline HTML with editable source and selected learning records embedded. ZIP and JSON are optional advanced formats. Use title + revision filenames, no ambiguous final/final2 names or repeated media copies. Read [reader output](references/reader-output.md), [content contract](references/content-contract.md) and [components](references/components.md) before generation. The schema in `references/notebook.schema.json` is authoritative. Reuse the renderer; do not create a new application for each subject.

The existing paper texture, hand font, Cornell layout and controls must come from the bundled reader, not newly written HTML/CSS/JS. A failed runtime download is a request for the fallback package, never permission to build a substitute interface. Preserve authored content while waiting. Before delivery, run `node scripts/notebook.mjs verify output/<title>-v<revision>.html --source notebook.json` (repository: `node tools/notebook.mjs verify ...`), or `python scripts/verify_reader.py ... --source notebook.json` in a Python environment. Both compare the artifact with the unchanged bundled reader; a matching JSON slot alone does not establish reader compatibility.

## Establish the brief: files first, then choices

1. If material status is unknown, the **first response only** asks the user to upload references (PDF, document, image, notes or question bank), or reply “没有文件 / no files”. Explain in that same response that without references you will retrieve reliable internet sources where available and create original explanations and diagrams; if retrieval is unavailable, say so. **End this response and wait. Do not ask for the field, topic, level or other brief details yet, and do not generate a tutorial.** Existing attachments or an explicit no-files answer satisfy this step; never ask again. If the user directly requests production with already sufficient instructions, preserve that authorization.
2. After files arrive or “no files” is confirmed, inspect what can be read. Use the host's native multiple-choice question control to ask for the missing field/topic first; provide concrete options suited to the files or request and allow free text. Then collect missing goal/scope, prior knowledge, difficulty, available time, course horizon, language/style, exercises and material fidelity (strict/guided/open) in short related batches. When no native choice control exists, offer concise numbered choices. Keep previous answers; do not repeatedly ask for information already provided. Default presentation is generous Cornell electronic paper with 2.05 line spacing, distinct paragraph spacing and useful illustrations interleaved with prose; the reader lets users change fonts, spacing and theme.
3. Summarize the agreed scope briefly and produce the tutorial. Do not insert another approval loop. Read [learning routes](references/routes.md) and [tutorial writing rules](references/writing.md) to choose depth and structure; do not infer a learner level or exercise preference when genuinely unspecified.

Strict source mode preserves uploaded wording, questions, answers, scope and order when explicitly requested; keep corrections separate from the original.

Prefer supplied materials. Supplement from reliable primary sources when retrieval is available; record source IDs and locators. State unresolved information. For PDF, document, image or scan input, use [OCR material preparation](references/ocr-workflow.md); preserve raw extraction with page locators, verify uncertain symbols and record corrections and glossary separately. For visual material read [multimodal production](references/multimodal.md). Ask once about retaining original images, program treatment or model redraw when style conversion is relevant; explain token use before model redraw.

## Native learning interactions

When a mechanism becomes clearer through changing quantities, stepping through states or examining passages, read [learning interactions](references/learning-interactions.md) and choose an appropriate native `exploration` block. Design the activity around a concrete learning result. Use plot for actual calculation, sequence for authored process replay, and reading for source-based interpretation. Keep formulas, units, data and explanatory prose aligned with the main lesson. Verify at least the initial state, a changed state, reset, offline persistence and print fallback; record the exercised paths in the final review. Do not embed executable scripts, invent an unimplemented widget, or describe authored replay as running code. Ordinary explanation remains available without operating a control.

## Generate and check

Read [discipline and learning stage](references/subject-pedagogy.md), [tutorial writing rules](references/writing.md), [emphasis and margin explanations](references/emphasis-and-margins.md), [direct writing review](references/writing-review.md) and [illustration production](references/multimodal.md). Plan and deliver useful hand-drawn illustrations alongside the explanation; use native SVG for structure/data and available image-generation tools for scenes when useful. Select figure size and aspect ratio before production. Explain the actual subject directly, with definitions, conditions, worked reasoning and sources. Avoid generic encouragement, assumptions of learner error, repeated conclusions, ornamental labels and mechanical “先……再……” instructions. Use subject-appropriate live-text blackboards, extracts, code containers and hand-drawn SVG relationships only where they carry useful content. Choose natural Chinese syntax; avoid habitual rebuttals and repetitive sentence patterns.

## Editorial priority: subject knowledge first

Follow the mandatory Chinese writing priority: user requirements, factual accuracy, necessary explanation, natural expression, then brevity. Apply anti-defensive-writing throughout planning, drafting and review. Write as an experienced textbook author: explain the subject, develop the reasoning and choose examples that reveal its mechanism. Delete sentences whose only purpose is to pre-empt an imagined objection, announce an obvious distinction or describe the author's caution. Every emphasis must identify something worth understanding or remembering. State substantive assumptions at the point where they enter the explanation. Follow the [Chinese de-AI writing rules](references/writing-review.md#中文去-ai-味): use natural subject–verb–object order where it fits Chinese, remove performative chat, ornamental metaphors, repeated content and empty summaries, and rewrite “不是……而是……” into a direct claim or parallel comparison. Review the actual prose, not just the prompt. Preserve exact quotations when requested.

Before outlining, read [discipline and learning stage](references/subject-pedagogy.md). Identify the knowledge activity, prerequisites and intended depth, then select the discipline's own forms of explanation and evidence. A literary reading develops context, language and interpretation; a machine-learning lesson develops models and their mathematical mechanisms; a business case develops an operating model with researched company evidence. Use these decisions to shape the lesson, rather than applying one universal outline. Explicit requests for exact source fidelity retain the supplied wording and structure.

Use a clean title hierarchy: one title per section, informative block headings where needed, no decorative subtitles, route strings or repeated notebook titles. Place explanation in the body and source details in source references.

Start from `assets/blank-notebook.json` (repository: `examples/blank-notebook.json`). Keep stable IDs; separate content and user state. Cornell cues are explanatory margin notes: prefer definitions, short examples, reasoning, figure readings or relevant conditions. Use an optional concrete title and a complete explanation, linked to its actual block and source phrase. Reserve questions for requested retrieval practice and reasoning with explicit context; omit trivial arithmetic, obvious distinctions and detached questions. Follow [emphasis and margin explanations](references/emphasis-and-margins.md). Section summaries are optional. Use one only for a useful synthesis or transfer relation; omit recaps that repeat the body, captions or earlier sections. The left paper column is removed; right and bottom margins also accept personal notes. Only include exercises when requested. Verify numbers, units, formulas, diagrams, option IDs and solutions. Subjective work receives reference points, not deterministic marks.

Use concrete topic titles; avoid repeated “怎样…”, “如何…” or “看图理解…” templates. Keep the main explanation in connected paragraphs. Use short titled `callout` blocks for useful supplementary conditions, unusual data or unit checks. Keep spacing compact while retaining 2.05 leading. Page borders and controls use the existing straight shared reader style; content annotations and diagram strokes retain their pencil style.

Authored emphasis is a required teaching decision. Identify the section's core concept, defining relationship and decisive condition before selecting exact source phrases for `study.marks`. Core terms and relationships use `bold`, with blue text (`kind: "red", color: "#285f9e"`) for the most important phrases; conditions that change a result use vermilion `#b1483d`. Combine these with sparse circles, underlines or dots that identify the reasoning. Choose phrases for their explanatory value, not frequency, position, convenient substring matching or mark-count targets. A final numeric answer, connective or generic word cannot stand in for the central idea. Verify actual bold/color text and source anchors in the delivered HTML. Follow the discipline-specific examples and semantic review in [emphasis and margin explanations](references/emphasis-and-margins.md). Never replace native marks with Markdown delimiters or flattened images. Preserve an explicit request for plain unmarked content.

Figures must include purposeful visual annotations: circle a decisive region, add a directional arrow, and use a short explanatory label where helpful. Use `figure.annotations` (normalized 0–100 viewport coordinates) for circles, arrows, checks and live-text labels; preserve the source geometry, labels and units. Include at least one annotated explanatory figure in a visual tutorial; plain captions alone do not satisfy this requirement. Keep authored figure annotations separate from personal `userState.figureMarks`. The downloaded reader must retain its built-in beginner guide and image annotation tools.

Review `contentReview` in the Node/Python build report for writing signals, teaching emphasis, margin-note anchors and repetition, figure coverage and large/unused assets. Review these semantically; the advisory checker never rewrites text or verifies facts. Keep genuine scope, negation, attribution and uncertainty.

The supplied builders/verifiers reject an authored tutorial with zero marks or anchors missing from the actual text. Review `studyMarks` in the build report for counts, kinds and unmarked pages. Empty runtime checks remain allowed. Add `--allow-unmarked` to validation/build/verification only for an explicit user request for unmarked content; never use it to bypass unfinished authoring.

An installed Skill contains a bundled CLI and reader; Node 20.19+ is sufficient:

```sh
node scripts/notebook.mjs validate notebook.json
node scripts/notebook.mjs build notebook.json --out output/my-tutorial
```

Run those paths relative to this Skill folder. In a toolkit checkout, use `node tools/notebook.mjs` instead; install dependencies and run `npm run build` only when no built runtime exists. Deliver only the actual `<title>-v<revision>.html` by default. It embeds fonts, assets, editable source and personal records. Keep JSON/ZIP build interfaces for optional advanced editing; provide those files only when requested. A4 portrait/landscape PDF is available through the reader's dedicated Export PDF panel and system print. Assets stay embedded without a duplicate assets folder. The builder removes unused Unicode font faces for authored notebooks; do not strip characters that appear in the content. Inspect the output, including mobile layout and exercised interactions. Report checks that could not run.

Keep the artifact focused on reading, annotations, exercises and saving records. Use the shipped compact common-character fonts; do not download or embed complete Unicode libraries for future editing. Uncommon characters must remain in the text and may use the system font. Obtain only media actually used in the lesson, directly from the source when needed, at a resolution suited to its displayed size; embed it before delivery. Keep technical labels and diagrams sharp. Do not include promotional videos, unused source images or duplicate copies of media. The saved HTML must not fetch resources to render its content.

For updates preserve `notebook.id` and existing entity IDs; include `extensions.baseRevision` equal to the source revision. Keep personal data in source. Removed or ambiguous text anchors remain visibly unresolved. Answer books use `notebook.parent` and `extensions.doubtLinks` from the contract.

## Delivery by environment

- Coding agents with repository and file tools work in the project checkout. Follow [workspace workflow](references/workspace-start.md), validate and build with the project CLI, and leave the finished HTML artifact in the workspace. Node alone is sufficient; Python is optional on this path.
- Conversation environments reuse accessible runtime files or automatically download `https://burntroses.github.io/paper-notebook/downloads/paper-notebook-conversation.zip`. Read `references/conversation-start.md`; `scripts/prepare_conversation.py` can acquire, verify and smoke-build the package. After an actual download failure or an explicit download restriction, output [the preset download response](references/responses/download-unavailable.zh-CN.txt) and wait for the ZIP instead of inventing a reader. Accept either the manual `paper-notebook-upload.zip` wrapper or its inner `paper-notebook-conversation.zip`; unwrap one layer in the execution environment when needed. Then build the authored `notebook.json` with Node or Python and attach the actual HTML. Once acquired, the package builds offline without dependency installation. Retain existing materials and answers.
- A conversation needs access to a runtime through direct download or existing files, either Node or Python, and file creation/attachment capabilities. For explicitly missing file delivery, use [the preset capability response](references/responses/file-delivery-unavailable.zh-CN.txt) before the brief and stop; do not substitute Markdown, TXT, HTML source in chat, or a claimed attachment. An unsuccessful network request is not proof of missing local file capabilities.

Read [conversation workflow](references/conversation-start.md) for chat-based file delivery. Markdown is an optional source/import format for material supplied by the user, never the final response for a notebook-generation request. Never invent attachments, build results or browser checks. Installation uses the complete package, including references, assets and scripts.
